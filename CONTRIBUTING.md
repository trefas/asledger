# Участие в разработке asledger

Документ описывает, как поднять проект, какие проверки обязательны и как
предлагать изменения.

## Требования к окружению

- **Go** — версия из `go.mod` (инструментальная цепочка ставится автоматически).
- **make** — команды сборки и проверок.
- **C-компилятор и cgo** — SQLCipher собирается через cgo. На Linux нужен
  `gcc` (например, `build-essential`); для arm64 — `gcc-aarch64-linux-gnu` и
  `libc6-dev-arm64-cross`, для Windows — MinGW (`x86_64-w64-mingw32-gcc`).
  Без CGO проект и тесты `store` не собираются.
- По желанию: `golangci-lint` (линтер) и `goreleaser` (проверка конфигурации
  релиза). Если их нет, соответствующие шаги `make check` пропускаются.

## Быстрый старт

```bash
git clone https://github.com/trefas/asledger.git
cd asledger
make check        # форматирование, статические проверки, тесты
make test-race    # тесты с детектором гонок
make build        # бинарники в bin/
make run          # демон: web :8777, API :8778
```

Книга создаётся в рабочем каталоге (`asledger.db`) и шифруется SQLCipher.
При первом запуске `asledgerd` спрашивает пароль в TTY и создаёт sidecar
`asledger.db.kdf.json`; пароль в конфигурации и argv не хранится. Путь и
адреса меняются флагами `-db`, `-web-addr`, `-api-addr` или файлом
конфигурации. Для старой незашифрованной книги выполните
`asledgerctl migrate-encrypt -db asledger.db` (интерактивно) или передайте
пароль через `-password-file`/`-password-fd`.

## Структура репозитория

```
cmd/asledgerd/       демон: web + REST API
cmd/asledgerctl/     обслуживание книги (migrate-encrypt, passwd, backup, import, export)
cmd/web/             отдельный запуск только web-интерфейса
pkg/core/            доменное ядро: store, engine, sync, hledger, report, reconcile
internal/api/        REST API (раздел 10 эпика)
internal/httpui/     web-интерфейс на html/template
internal/integration/ интеграционный стенд (сервер + клиенты)
internal/release/    статические проверки артефактов релиза
templates/charts/    шаблонные планы счетов
assets/logo/         лого и иконки
docs/                документация
packaging/systemd/   юнит и env-файл службы Linux
```

## Схема веток и коммиты

- `main` — стабильная ветка; сюда попадают только проверенные изменения.
- Небольшие изменения допускается коммитить в `main` напрямую; крупные —
  через ветку `feature/<кратко>` или `fix/<кратко>` и pull request.
- Сообщения коммитов — **на русском**, содержательные: что и зачем сделано.
  Рекомендуется conventional-префикс (`feat:`, `fix:`, `docs:`, `chore:`) —
  по нему GoReleaser группирует release notes. В конце сообщения — ссылки на
  задачи: `(#12, #34)`.
- Один коммит — одна логическая правка; тесты и документация идут вместе с
  кодом, который они описывают.

## Обязательные проверки

Перед отправкой изменений должны проходить:

```bash
make check        # fmt-check, vet, lint-money, lint-trace, goreleaser, golangci-lint, тесты
make test-race    # гонки
make cover-check  # общий порог покрытия (COVERAGE_MIN, по умолчанию 70 %)
```

CI выполняет то же самое на Linux и Windows (`.github/workflows/ci.yml`).
Красный CI — блокер для слияния.

Что проверяется дополнительно:

- `scripts/check-no-float.sh` — в денежном коде нет `float32`/`float64`;
  суммы хранятся в копейках (`money.Kop`).
- `scripts/check-traceability.sh` — карта
  [docs/traceability.md](docs/traceability.md) связывает каждый критерий
  приёмки эпика с существующим автотестом; новый критерий без теста роняет CI.
- Тесты с трассируемыми именами `TestASL_<раздел>_<пункт>` обязательны для
  критериев приёмки (см. [docs/testing.md](docs/testing.md)).

## Процесс pull request

1. Форкните репозиторий и создайте ветку от `main`.
2. Внесите изменение, добавьте тесты и обновите документацию.
3. Локально прогоните `make check` и `make test-race`.
4. Откройте PR: опишите проблему, решение и способ проверки; сошлитесь на
   задачу (`Closes #N`).
5. Дождитесь зелёного CI и ревью. Правки — новыми коммитами в ту же ветку.
6. После слияния ветка удаляется; релиз публикуется отдельно по тегу
   (см. [docs/release.md](docs/release.md)).

## Стиль кода

- Комментарии, сообщения об ошибках и документация — **на русском**.
- Публичные сущности документируются комментарием, начинающимся с имени.
- Ошибки оборачиваются с контекстом (`fmt.Errorf("...: %w", err)`).
- Деньги — только `money.Kop`; форматирование — через `money.Kop.String()`.
- Новые HTTP-маршруты и коды ошибок описываются в `docs/api.md` и
  `docs/validation-codes.md`.
- Новые экраны и поведение web — в `docs/web.md`.
