# REST API asledger

REST API работает на порту **8778**, все маршруты — под `/api/v1`. Сервер —
единственная точка записи книги: онлайн-проводки и пакеты синхронизации
проходят через движок и матрицу правил ASL-2.2.

- Формат данных — JSON (`Content-Type: application/json; charset=utf-8`).
- Денежные величины — целые числа в копейках (`amount_kop`), без чисел с
  плавающей точкой.
- Дата — RFC 3339 (`2026-10-19T12:00:00Z`).

## Аутентификация

Персональный токен устройства передаётся в заголовке:

```
Authorization: Bearer <токен>
```

Токен выдаётся один раз при привязке устройства (`POST /auth/pair`). В книге
хранится только SHA-256 токена, открытое значение не сохраняется и не
логируется. Отозвать токен можно через `DELETE /auth/token`.

### POST /api/v1/auth/pair

Привязка устройства и выдача токена.

Запрос:

```json
{ "name": "Андрей", "secret": "пароль", "client_id": "телефон-андрея" }
```

Ответ `200`:

```json
{ "token": "…", "client_id": "телефон-андрея", "user_id": 1, "user_name": "Андрей" }
```

Ошибки: `401 ERR_AUTH_FAILED` — неверные имя или секрет.

### POST /api/v1/auth/enroll

Привязка устройства **без пароля** — для клиентов, у которых на первом экране
только адрес сервера и порт (Android). Доступна только из локальной сети и
отключается настройкой книги `привязка_устройств = deny`.

Запрос:

```json
{ "client_id": "android-…", "device_name": "Телефон", "user_id": 1 }
```

`user_id` необязателен. Если в книге один пользователь, он выбирается
автоматически; если несколько — сервер просит выбрать.

Ответ `200` — как у `pair`: `token`, `client_id`, `user_id`, `user_name`.

Ответ `409`, когда нужно выбрать пользователя:

```json
{ "error": { "code": "ERR_ENROLL_USER_REQUIRED", "message": "выберите пользователя…" },
  "users": [ { "id": 1, "name": "Андрей" }, { "id": 2, "name": "Мария" } ] }
```

Ошибки:

| Код | HTTP | Когда |
| --- | --- | --- |
| `ERR_ENROLL_FORBIDDEN` | 403 | запрос не из локальной сети |
| `ERR_ENROLL_DISABLED` | 403 | привязка запрещена настройкой |
| `ERR_ENROLL_NO_USERS` | 409 | в книге ещё нет пользователей |
| `ERR_ENROLL_USER_REQUIRED` | 409 | несколько пользователей, нужен выбор |
| `ERR_ENROLL_USER_UNKNOWN` | 422 | передан несуществующий `user_id` |

Отозвать токен можно через `DELETE /auth/token` или в web-интерфейсе
(раздел «Устройства»).

### DELETE /api/v1/auth/token

Отзыв токена текущего устройства. Ответ `200`:

```json
{ "status": "revoked", "client_id": "телефон-андрея" }
```

## Онлайн-проводка

### POST /api/v1/transactions

Быстрая онлайн-проводка. Клиент присылает **роли** строк, стороны
(DEBIT/CREDIT) назначает сервер. Проводка оформляется коммитом из одной
операции и попадает в хэш-цепочку.

Запрос:

```json
{
  "op_type": "трата",
  "uuid": "1f0c…",
  "date": "2026-10-19T12:00:00Z",
  "description": "Продукты",
  "entries": [
    { "account_id": 12, "amount_kop": 25000, "role": "расход" },
    { "account_id": 4,  "amount_kop": 25000, "role": "источник" }
  ]
}
```

Ответ `201`:

```json
{
  "id": 41,
  "uuid": "1f0c…",
  "op_type": "трата",
  "date": "2026-10-19T12:00:00Z",
  "lines": [
    { "account_id": 12, "amount_kop": 25000, "side": "DEBIT" },
    { "account_id": 4,  "amount_kop": 25000, "side": "CREDIT" }
  ]
}
```

Повтор с тем же `uuid` идемпотентен: возвращается прежняя проводка.

Если сервер находит совпадение по типу, дате, счетам и суммам в пределах дня,
ответ дополняется плашкой «Возможный дубль» (`duplicates` — uuid новой проводки
и uuid уже записанных совпадений). Коммит при этом принимается: отменить запись
можно сторно.

### POST /api/v1/transactions/{uuid}/reverse

Сторно проводки: счета те же, стороны противоположные, `reverses_id` указывает
на отменяемую запись. Тело запроса не требуется. Повторная отмена идемпотентна и
возвращает уже созданное сторно. Ответ — `201` с проводкой-сторно.

## Отчёты и сверка

Все отчёты строятся свёрткой журнала (остатки не хранятся) и требуют токен.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/v1/reports/balances` | остатки по счетам с иерархическими итогами |
| `GET /api/v1/reports/turnovers` | обороты по узлу дерева за период |
| `GET /api/v1/reports/expenses` | расходы по членам семьи за период |
| `GET /api/v1/reports/journal` | журнал проводок с фильтрами и страницами |
| `GET /api/v1/reports/discrepancies` | расхождения по счетам (последняя сверка) |
| `POST /api/v1/reconcile` | сверка счёта и генерация корректировки |

**Остатки** (`balances`): параметры `include_archived`, `include_empty`. Ответ —
строки `rows` (путь, тип, уровень, собственный остаток `own_kop` и итог
`total_kop` вместе с поддеревом, форматированные значения `own`/`total`), итоги
`assets_kop`, `liabilities_kop`, `net_worth_kop` и список `negative` — счета с
отрицательным остатком (подсветка минусов).

**Обороты** (`turnovers`): параметры `node` (полный путь узла; по умолчанию вся
книга), `from`/`to` (ГГГГ-ММ-ДД, границы включают весь день), `include_archived`,
`include_empty`. Обороты нелистовых веток считаются по префиксу пути. Ответ —
`opening_kop`, `debit_kop`, `credit_kop`, `closing_kop` по каждому счёту.

**Расходы по членам семьи** (`expenses`): параметры `from`/`to`. Расход считается
по строкам счетов типа «расход» (ΣDEBIT − ΣCREDIT), сторно уменьшает показатели.
Ответ — `actors` (автор, итог, разбивка по статьям) и `total_kop`.

**Журнал** (`journal`): параметры `from`/`to`, `account` (поддерево по пути),
`account_id`, `actor_id`, `op_type`, `source`, `amount_from`/`amount_to` (копейки,
по сумме проводки), `page` (с 1), `per_page` (по умолчанию 50, не больше 500).
Ответ — `total`, `page`, `per_page`, `rows` (проводки с разрешёнными именами
счетов и авторов).

**Расхождения** (`discrepancies`): последняя сверка по каждому счёту. Расхождение
считается от текущего остатка, поэтому после корректировки равно нулю. В ответе —
факт, текущий остаток, расхождение и признак `adjustable`.

### POST /api/v1/reconcile

Сверка счёта с фактическим остатком:

```json
{ "account_id": 12, "fact_kop": 90000, "generate": true, "uuid": "1f0c…" }
```

- `fact_kop` — фактический остаток (копейки);
- `date` — дата корректировки (ГГГГ-ММ-ДД), по умолчанию текущая;
- `generate` — создать корректировку на расхождение;
- `uuid` — идентификатор корректировки (по умолчанию генерируется).

Ответ `200`: `fact_kop`, `balance_kop` (расчётный остаток на момент сверки),
`difference_kop` (факт минус расчётный), форматированные значения и `transaction`
— сгенерированная корректировка, если запрошена. Корректировка идёт через
служебный счёт «Капитал:Корректировка», поэтому балансовое уравнение
(ΣDEBIT = ΣCREDIT) сохраняется.

Корректировка доступна только для активов, обязательств и капитала; для доходов
и расходов возвращается `422 ERR_RECONCILE_NOT_ADJUSTABLE`.

## Синхронизация по модели git

Сервер — master-ветка: единственная точка, задающая порядок коммитов.
Устройство держит снапшот книги и коммитит офлайн-проводки.

### GET /api/v1/sync/snapshot

Полный снапшот книги (клонирование на новое устройство): план счетов,
пользователи без секретов, настройки, проводки со строками, `head_seq` и
`chain_hash`. Версия формата — `format_version`.

### POST /api/v1/sync/push

Коммит пакета операций.

Запрос:

```json
{
  "base_seq": 12,
  "commit_id": "устройство-1:7",
  "operations": [
    { "op_type": "трата", "uuid": "…", "date": "…",
      "entries": [ { "account_id": 12, "amount_kop": 25000, "role": "расход" },
                   { "account_id": 4,  "amount_kop": 25000, "role": "источник" } ] }
  ]
}
```

Ответ `200`:

```json
{
  "status": "accepted",
  "commit_id": "устройство-1:7",
  "result_seq": 13,
  "applied": ["…"],
  "warnings": [],
  "duplicates": [
    { "uuid": "…", "existing": ["…"] }
  ]
}
```

`duplicates` (есть только при совпадениях) — плашка «Возможный дубль»: uuid новой
проводки и uuid уже записанных совпадений по типу, дате, счетам и суммам. Дубль
не блокирует приём пакета; отменить запись можно сторно.

Статусы:

| Статус | HTTP | Когда |
| --- | --- | --- |
| `accepted` | 200 | пакет принят полностью |
| `accepted-with-warnings` | 200 | принят с предупреждениями (rebase, возможные дубли, повторы uuid) |
| `rejected` | 422 | пакет отклонён целиком, книга не изменена |

Отклонённый пакет возвращает тело:

```json
{
  "status": "rejected",
  "commit_id": "устройство-1:7",
  "result_seq": 12,
  "warnings": [],
  "error": { "code": "ERR_MATRIX_CELL", "message": "…" }
}
```

Правила:

- `base_seq == head_seq` — **fast-forward**: пакет применяется целиком в одной
  транзакции БД; любая ошибка валидации отклоняет пакет без изменений.
- `base_seq < head_seq` — **rebase**: операции переигрываются поверх головы,
  конфликты и дубли попадают в `warnings`.
- Повторная отправка того же `commit_id` с тем же содержимым даёт тот же ответ
  (`status`, `result_seq`, `warnings`).
- Успешный push увеличивает `head_seq` ровно на число применённых операций.

### GET /api/v1/sync/pull?since=N&hash=…

Дельта журнала изменений с `seq > N`.

Параметры:

- `since` — последний известный клиенту `seq` (по умолчанию 0);
- `hash` — последний известный хеш цепочки (необязательный): при расхождении
  ответ содержит `resync_required: true`, клиенту нужен полный ресинк со
  снапшота.

Ответ:

```json
{
  "format_version": 1,
  "since": 12,
  "head_seq": 14,
  "chain_hash": "…",
  "changes": [ { "seq": 13, "entity": "transactions", "entity_id": 41, "op": "insert", "changed_at": "…" } ],
  "transactions": [ { "id": 41, "uuid": "…", "op_type": "трата", "lines": [ … ] } ],
  "accounts": [ … ],
  "accounts_read_only": true,
  "commits": [ { "id": 9, "base_seq": 12, "result_seq": 13, "hash": "…", "ops_json": "…" } ],
  "resync_required": false
}
```

План счетов отдаётся целиком и помечен `accounts_read_only: true`: изменения
плана — только через web-интерфейс.

### Хэш-цепочка

Звено цепочки: `hash = SHA-256(предыдущий хеш || ops_json)`, где `ops_json` —
каноническая сериализация пакета (фиксированный порядок полей). Клиент
досчитывает цепочку после pull: совпадение доказывает идентичность реплик,
расхождение — сигнал о полном ресинке.

Звено, `head_seq` и признак rebase вычисляются внутри одной транзакции записи
коммита под общей блокировкой. Поэтому одновременные push выстраиваются в
линейную цепочку (два клиента на одном `base_seq`: первый проходит fast-forward,
второй получает rebase-предупреждение), а не разветвляют её.

## Подсказки счетов

### GET /api/v1/accounts/suggest?q=…&op_type=…&limit=…

Параметры: `q` — часть имени или пути (регистр кириллицы не важен), `op_type` —
тип операции для фильтра по матрице, `limit` — предел выдачи (по умолчанию 20).

Ответ:

```json
{
  "items": [ { "id": 8, "name": "Зарплата", "full_path": "Доходы:Зарплата",
               "type": "доход", "is_leaf": true, "usable": true } ],
  "accounts_read_only": true
}
```

Листовые счета идут первыми и помечаются `is_leaf: true`; папки отдаются с
пометкой `is_leaf: false` и `usable: false`. `usable` учитывает допустимость
типа счёта для текущей операции.

## Роли и стороны матрицы

### GET /api/v1/engine/roles?op_type=…

Единый источник правил для мобильных клиентов: роли строк, их стороны и
допустимые типы счетов. Клиент группирует роли по `DEBIT`/`CREDIT` и не
дублирует матрицу ASL-2.2.

Ответ для `op_type=трата`:

```json
{
  "op_type": "трата",
  "title": "Трата",
  "roles": [
    { "role": "расход", "side": "DEBIT", "account_types": ["расход"], "direction_required": false },
    { "role": "источник", "side": "CREDIT", "account_types": ["актив"], "direction_required": false }
  ],
  "min_debit": 1,
  "min_credit": 1,
  "reserved": { "credit": ["пассив"] },
  "accounts_read_only": true
}
```

Для переоценки и корректировки сторона зависит от направления: возвращается
роль `корректируемый` с пустым `side` и `direction_required: true`.

Ошибки: `400 ERR_REQUEST_INVALID` — нет `op_type`; `422 ERR_OP_TYPE_UNKNOWN` —
неизвестная операция.

## Планы счетов, импорт и экспорт

### GET /api/v1/charts/templates

Список шаблонных планов счетов из каталога `charts_dir`:

```json
{ "templates": [ { "file": "personal.json", "name": "Личный", "accounts": 33 } ] }
```

### POST /api/v1/import

Импорт файла. Поддерживаются `chart-json` (вложенный формат `children`) и
`hledger` (plaintext-книга, см. [hledger.md](hledger.md)):

```json
{ "format": "chart-json", "content": "{ … }" }
{ "format": "hledger", "mode": "гибкий", "file_name": "book.journal", "content": "2026-01-15 …" }
```

Ответ для `chart-json`: `{ "format": "chart-json", "created": 5, "existing": 0 }`.

Ответ для `hledger` — отчёт об импорте:

```json
{
  "format": "hledger", "mode": "гибкий", "accepted": 12, "skipped": 1, "duplicates": 0,
  "created_accounts": ["Расходы:Продукты"], "rejected": false,
  "problems": [ { "line": 42, "message": "счёт «Недвижимость» отсутствует в плане счетов" } ]
}
```

Проблемы данных не считаются ошибкой запроса: ответ `200` с отчётом. Строгий
режим (`"mode": "строгий"`) при любой проблеме не меняет книгу и возвращает
`"rejected": true`. Повторный импорт того же файла идемпотентен: проводки
попадают в `duplicates`.

### GET /api/v1/export?format=json|csv|hledger

Экспорт книги.

- `json` — полный снапшот книги (формат синхронизации);
- `hledger` — plaintext-книга hledger (файл `asledger.journal`);
- `csv` — журнал или отчёт (файл `asledger-<отчёт>.csv`). Параметр `report`
  выбирает отчёт: `journal` (по умолчанию), `balances`, `turnover`; для
  оборотов период задаётся `from` и `to` (ГГГГ-ММ-ДД).

CSV отдаётся в UTF-8 с меткой порядка байтов и разделителем `;` — так его
открывают электронные таблицы без искажений кириллицы.

## Ошибки

Единый конверт ошибки:

```json
{ "error": { "code": "ERR_UNBALANCED", "message": "дебет 25000 коп. не равен кредиту 20000 коп.",
             "account": "Активы:Наличные", "cell": "трата/CREDIT/доход" } }
```

- `code` — машинный код (полный список — [validation-codes.md](validation-codes.md));
- `message` — понятное пользователю сообщение на русском;
- `account`, `amount_kop`, `cell` — контекст, если он есть.

Коды HTTP: `400` — некорректный запрос, `401` — нет или неверен токен,
`404` — маршрут не найден, `405` — неверный метод, `422` — нарушение
инвариантов движка, `500` — внутренняя ошибка.

Все ответы содержат заголовок `X-Request-Id`.
