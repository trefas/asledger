# Безопасность и шифрование книги

Документ фиксирует модель угроз, выбор SQLCipher-драйвера и жизненный цикл
мастер-ключа для `v1.3.0`–`v1.3.2` и обновления S24
(эпик [#138](https://github.com/trefas/asledger/issues/138)). Результаты
spike — [#148](https://github.com/trefas/asledger/issues/148), модель угроз и
решения по ключу — [#149](https://github.com/trefas/asledger/issues/149).

Статус: `store`, источники ключа, миграция plaintext → SQLCipher, смена
пароля, Electron-экран пароля и совместимость Android (#153) реализованы в
#150–#154. Релиз `v1.3.0` (#155) опубликован; `v1.3.1` — патч брендинга
desktop (#157/#158) без изменений модели угроз, SQLCipher и формата книги.
S24 (#160) обновляет драйвер до `meow-io/go-sqlcipher v1.1.2`
(SQLCipher 4.19.0, SQLite 3.53.4); это вошло в опубликованный `v1.3.2`.
Формат книги, DSN, KDF и Android-совместимость не меняются. Обычный запуск
с незашифрованной книгой требует явного `-allow-plaintext`; частичный
SQLCipher-релиз не выпускается.
Android JVM-тест обновлён под зашифрованный сервер, но локально не
запускался: в среде разработки нет JDK и Android SDK.

## 1. Что защищаем

Активы:

- финансовые данные книги: счета, проводки, остатки, отчёты, история;
- мастер-ключ книги и пароль пользователя;
- резервные копии книги и журналы;
- токены устройств и пользовательские секреты API.

SQLCipher шифрует страницы книги, WAL и резервные копии, созданные через
SQLCipher. Он не заменяет аутентификацию API, TLS, защиту ОС и защиту
Android-устройства.

## 2. Модель угроз

| Угроза | Что делаем | Остаточный риск |
| --- | --- | --- |
| Украден диск, ноутбук или резервная копия | SQLCipher AES-256, ключ не хранится рядом с книгой в открытом виде | Если устройство разблокировано или ключ лежит в системном хранилище этого пользователя, защита не срабатывает |
| Книга попала в облачную папку или общий каталог | Файл зашифрован; соль и параметры KDF не являются секретом | Размер файла, число страниц и время работы могут выдать метаданные; облачный провайдер видит факт синхронизации |
| Другой пользователь ОС | Права `0600` на книгу и sidecar, `0700` на каталог данных; системное хранилище ключа привязано к пользователю | Администратор/root и пользователь с тем же аккаунтом защиту обходят |
| Вредоносный процесс в сеансе пользователя | Ключ живёт в памяти только во время работы; renderer и книга не получают ключ | Процесс с правами пользователя может прочитать память, перехватить ввод или keychain |
| Утечка через журнал, crash-дамп, `argv` или env | Секреты не пишутся в журнал; пароль/ключ не передаются в `argv` и обычных env; core-дампы отключены для службы | Сторонние библиотеки и ОС могут оставить копию в swap/hibernation |
| Потеря устройства | Шифрование at-rest + блокировка ОС | Если устройство разблокировано, данные доступны |
| Офлайн-подбор пароля | Argon2id с солью и памятью 64 МиБ; предупреждение о сложном пароле | Слабый пароль всё равно подбирается; восстановления пароля нет |
| Подмена/откат файла | SQLCipher HMAC обнаруживает повреждение страниц | Замена книги на старую зашифрованную копию не обнаруживается; нужны резервные копии и контроль версий |
| Сетевой атакующий в локальной сети | Вне рамок SQLCipher: API остаётся локальным, без TLS | Трафик и токены в локальной сети нужно защищать отдельно |

### Границы защиты

SQLCipher защищает данные **только в состоянии покоя**, когда ключ отсутствует
в памяти. Он не защищает от:

- root/администратора, malware с правами пользователя, keylogger, screen
  capture, чтения памяти процесса;
- вредоносного или подменённого бинарника Electron/`asledgerd`;
- атак по сторонним каналам (размер файла, тайминги, факт обращения к диску);
- сетевых атак, отсутствия TLS и слабых токенов API;
- незашифрованной Android Room-базы: Android-клиент и его локальная реплика
  в эту модель не входят.

Для снижения остаточных рисков рекомендуется полнодисковое шифрование ОС,
блокировка экрана, отдельный пароль книги и резервные копии в защищённом
месте.

## 3. Выбор драйвера SQLCipher

### Рассмотренные варианты

| Вариант | Плюсы | Ограничения | Решение |
| --- | --- | --- | --- |
| `modernc.org/sqlite` (до v1.3.0) | Чистый Go, `CGO_ENABLED=0`, простая кросс-сборка | Не поддерживает SQLCipher; `PRAGMA key` не шифрует | Не подходит |
| `github.com/mutecomm/go-sqlcipher/v4 v4.4.2` | Самодостаточный cgo-драйвер, SQLCipher внутри, Linux/Windows, кросс-сборка, MIT/BSD/public domain | SQLCipher 4.4.2 (2020), SQLite 3.33.0; upstream не обновляется с 2020 года | Использовался в v1.3.0–v1.3.1; заменён в S24 (#160) |
| `github.com/WissCore/go-sqlcipher/v4 v4.15.1` | Форк mutecomm с CI, SBOM и подписанными релизами; SQLCipher 4.15.0, SQLite 3.53.0 | Отстаёт от актуального SQLCipher 4.19.0/SQLite 3.53.4; SQLite 3.53.0 ещё содержит FTS5 CVE-2026-11822/11824 | Запасной вариант |
| `github.com/meow-io/go-sqlcipher v1.1.2` | SQLCipher 4.19.0, SQLite 3.53.4, CI Linux/macOS/Windows, libtomcrypt, raw key | Module path без `/v4`; мало звёзд, нет подписанных GitHub Releases/SBOM | **Выбран в S24 (#160)** |
| Официальный SQLCipher + `mattn/go-sqlite3` | Актуальный SQLCipher, знакомый драйвер | Нужна `libsqlcipher` под каждую цель; сложная кросс-сборка и упаковка | Не выбран для MVP; резервный путь |
| `ncruces/go-sqlite3`, `glebarez/go-sqlite` | Чистый Go/WASM | Нет штатного SQLCipher-шифрования | Не подходит |

Лицензии выбранного драйвера: MIT (код `mattn/go-sqlite3`), BSD-3-Clause
(SQLCipher, Zetetic LLC), public domain (SQLite, LibTomCrypt). Они совместимы
с MIT-лицензией проекта.

### Почему выбран `meow-io/go-sqlcipher v1.1.2`

- SQLCipher 4.19.0 (сентябрь 2026) и SQLite 3.53.4 — самые свежие версии
  среди проверенных драйверов. SQLCipher 4.19.0 включает исправления
  `sqlcipher_export` и `hexkey`, SQLite 3.53.4 — исправления FTS5
  CVE-2026-11822/11824 и более ранних CVE.
- SQLCipher встроен в драйвер, не требует системной `libsqlcipher`,
  pkg-config или OpenSSL: используется вендорный libtomcrypt.
- Проверена сборка под Linux amd64, Linux arm64 и Windows amd64, в том числе
  через GoReleaser-cross; Linux-бинарники статические, Windows зависит только
  от `ADVAPI32.dll`, `KERNEL32.dll` и `msvcrt.dll`.
- Драйвер работает через `database/sql`; бизнес-логика `store` не меняется.
- Есть режим raw key, который позволяет использовать собственный KDF и не
  платить SQLCipher KDF на каждом открытии.
- Книга, созданная SQLCipher 4.4.2, открывается, проходит `integrity_check`,
  миграции и `sqlcipher_export`; обратное открытие книги 4.19.0 драйвером
  4.4.2 также проверено. Регрессия закреплена тестом
  `TestOpenBookFromSQLCipher442` и фикстурой
  `pkg/core/store/testdata/sqlcipher-4.4.2.db`.

### Почему не WissCore

`WissCore/go-sqlcipher/v4 v4.15.1` — более осторожный вариант с CI, SBOM,
OpenSSF Scorecard и подписанными релизами. Он также прошёл тесты и
кросс-сборку, но использует SQLCipher 4.15.0/SQLite 3.53.0: в SQLite 3.53.0
ещё присутствуют FTS5 CVE-2026-11822/11824, исправленные в 3.53.2, а нового
релиза после мая 2026 года нет. Поэтому WissCore остаётся запасным
вариантом, если meow-io перестанет обновляться или выявится несовместимость.

### Риски выбранного драйвера

- meow-io — небольшой форк с малым числом звёзд и без подписанных GitHub
  Releases/SBOM. Компенсация: точный пин `v1.1.2` (commit `23363a4`) и
  контрольные суммы в `go.sum`, аудит diff относительно `mutecomm@25f68ad`,
  проверка отсутствия сетевых/exec-вызовов в Go-коде драйвера,
  регрессионная фикстура и пересмотр зависимости при каждом обновлении.
  WissCore — запасной источник.
- Module path `github.com/meow-io/go-sqlcipher` не содержит `/v4`. Версия
  фиксируется как `v1.1.2`; публичный API и DSN от этого не меняются.
- cgo усложняет сборку и CI: нужны компиляторы под каждую цель и статическая
  линковка.
- Статическая glibc-сборка имеет ограничения для `getaddrinfo`/NSS; поэтому
  используются теги `netgo osusergo` и `sqlite_omit_load_extension`.
- Windows-бинарник зависит от `KERNEL32.dll` и `msvcrt.dll`; SQLCipher DLL не
  требуется.
- macOS-артефакты в `v1.3.2` не выпускаются: нет подписи и нотаризации.
  Драйвер собирается под darwin, но это не проверенный релизный сценарий.
  Решение пересматривается вместе с #145/#155.
- При появлении критичной и достижимой уязвимости релиз блокируется до
  обновления драйвера. Откат на plaintext или `modernc.org/sqlite` запрещён.

### Проверка CVE (2026-10-25)

**До S24 (v1.3.1).** Проверка шла по NVD для SQLCipher 4.4.2 и встроенного в
драйвер SQLite 3.33.0; версия SQLite проверена через
`select sqlite_version()`.

- SQLCipher: [CVE-2021-3119](https://nvd.nist.gov/vuln/detail/CVE-2021-3119)
  (CVSS 3.1 — 7.5, high) — NULL pointer dereference в `sqlcipher_export` и
  `sqlite3StrICmp`; нужен специально сформированный SQL. Исправлена в
  SQLCipher 4.4.3.
- SQLite 3.33.0: CVE-2021-20227 (5.5), CVE-2022-35737 (7.5),
  CVE-2023-7104 (5.5), CVE-2025-6965 (7.7), CVE-2025-70873 (7.5),
  CVE-2026-11822 и CVE-2026-11824 (7.8). Часть затрагивает расширения
  session/zipfile/FTS5, которые не собираются.
- В `asledger` нет канала, через который удалённый клиент передаёт
  произвольный SQL: API работает с параметризованными запросами и доменными
  командами, Android-клиент использует только REST, а
  `sqlcipher_export('migrated')` вызывается с константой при локальной
  миграции/смене пароля. Поэтому для `v1.3.0`/`v1.3.1` эти уязвимости
  считались недостижимыми через сеть; это было осознанное принятие риска, а
  не отсутствие проверки.

**После S24.** SQLCipher 4.19.0 / SQLite 3.53.4.

- CVE-2021-3119 закрыта обновлением SQLCipher (4.4.3+).
- CVE-2026-51936 (SQL injection в `sqlcipher_export` до 4.15.0) закрыта;
  SQLCipher 4.19.0 дополнительно исправляет escaping имён файлов миграции,
  алиасов БД и `hexkey` URI.
- SQLite 3.53.4 включает исправления перечисленных выше CVE, в том числе
  CVE-2025-6965 (3.50.2+) и CVE-2026-11822/11824 (3.53.2+).
- Сборка не включает `sqlite_fts5`, session и zipfile; произвольный SQL от
  клиента по-прежнему не принимается. Остаточный риск связан с небольшим
  форком и будущими CVE, а не с известными записями на 2026-10-25.
- Публичных CVE для SQLCipher 4.19.0 на 2026-10-25 в NVD не найдено; это не
  гарантия отсутствия уязвимостей. При выходе SQLCipher 4.20+/SQLite 3.54+
  зависимость пересматривается в рамках планового обновления S24.

## 4. KDF и параметры

Для `v1.3.0` принимается **Argon2id** из `golang.org/x/crypto/argon2`, а не
встроенный KDF SQLCipher:

| Параметр | Значение |
| --- | --- |
| Алгоритм | Argon2id, версия 0x13 |
| Соль | 16 случайных байт на книгу |
| Память | 64 МиБ (`memory_kib = 65536`) |
| Итерации | 3 |
| Параллелизм | 4 |
| Длина ключа | 32 байта |
| Назначение | ключ SQLCipher в raw-режиме |

Почему не SQLCipher KDF:

- встроенный KDF SQLCipher 4 — PBKDF2-HMAC-SHA512, 256 000 итераций; в spike
  открытие существующей книги занимало ~257 мс на соединение;
- raw-ключ после Argon2id открывается без KDF SQLCipher (в spike — 0 мс);
- производный ключ можно хранить в системном хранилище, не сохраняя пароль;
- параметры Argon2id можно версионировать в sidecar и менять без пересборки
  формата SQLCipher.

Замер Argon2id с параметрами выше на машине разработки — около 38 мс.
Параметры могут быть увеличены после профилирования на слабых машинах, но
только с версией в sidecar.

### Sidecar с параметрами KDF

Рядом с книгой создаётся sidecar `<db>.kdf.json`: для книги `asledger.db` это
`asledger.db.kdf.json`. Имя привязано к файлу книги, чтобы несколько книг в
одном каталоге не перепутали параметры KDF.

```json
{
  "version": 1,
  "kdf": "argon2id",
  "salt": "<base64url, 16 байт>",
  "memory_kib": 65536,
  "iterations": 3,
  "parallelism": 4,
  "key_len": 32,
  "cipher": "sqlcipher",
  "cipher_compatibility": 4,
  "page_size": 4096
}
```

Это **не секрет**: соль и параметры нужны для повторного вывода ключа из
пароля. В sidecar нет ни пароля, ни KDF-результата. Файл пишется атомарно с
правами `0600`, входит в резервную копию и не синхронизируется отдельно от
книги.

Если sidecar потерян, пароль уже не выведет ключ. Книгу можно открыть
сохранённым ключом из системного хранилища, если пользователь включал
«Запомнить»; иначе остаётся резервная копия и старый ключ. Это нужно явно
описывать при миграции.

Версионирование: `version` sidecar, `kdf`, `cipher_compatibility` и
`page_size`. При смене KDF или формата создаётся новый sidecar, а миграция
книги выполняется отдельно; старые параметры не перезаписываются молча.

## 5. Мастер-ключ и пароль

Мастер-ключ — 32-байтовый ключ SQLCipher, полученный из пароля через
Argon2id. Он не хранится в `config.json`, не передаётся в `argv` и не пишется
в журнал.

### Источники пароля

| Источник | Как работает | Ограничения |
| --- | --- | --- |
| Интерактивный ввод | `asledgerd`/`asledgerctl` читает пароль с TTY без эха | Нет TTY у службы; пароль остаётся в памяти процесса |
| stdin/pipe | Electron пишет пароль в stdin дочернего `asledgerd` (`-password-fd=0`), затем закрывает поток | Нельзя логировать stdin; нужен таймаут и понятная ошибка |
| fd | `-password-fd=N`; родитель передаёт уже открытый дескриптор | Дескриптор не должен наследоваться другими процессами |
| Файл | `-password-file=PATH` или `ASLEDGER_PASSWORD_FILE`; путь не является секретом | Файл `0600`, владелец — пользователь службы; удалить после чтения |
| systemd | `LoadCredential=asledger-password:/etc/asledger/asledger-password`; служба читает `$CREDENTIALS_DIRECTORY/asledger-password` | Нужен systemd с поддержкой credentials; исходный файл недоступен другим |
| Windows-служба | DPAPI-защищённый файл или Credential Manager; путь/имя передаётся службе через `-password-file` | DPAPI привязан к пользователю/машине; администратор может расшифровать |
| Системное хранилище Electron | `safeStorage` (Keychain/DPAPI/Secret Service) хранит **ключ**, не пароль; ключ передаётся через `-key-fd`/`-key-file` | Linux без keyring не годится; same-user malware может прочитать |

Флаги и переменные:

- `asledgerd` и `asledgerctl` принимают `-password-file`, `-password-fd`,
  `-key-file`, `-key-fd`; `-password-fd=0`/`-key-fd=0` читают stdin.
- `ASLEDGER_PASSWORD_FILE` и `ASLEDGER_KEY_FILE` задают только **пути** к
  секретам. Сырой пароль/ключ в env не поддерживается.
- `-allow-plaintext` и `ASLEDGER_ALLOW_PLAINTEXT=1` — только явный режим
  миграции/тестов; обычный запуск его не включает.
- systemd credentials автоматически читаются из
  `$CREDENTIALS_DIRECTORY/asledger-password` или `asledger-key`, если другие
  источники не заданы.

Запрещено:

- `--password`, `--key`, `ASLEDGER_PASSWORD`, `ASLEDGER_KEY` и любые обычные
  переменные окружения с секретом;
- хранение пароля или ключа в `config.json`, `electron-store`, localStorage,
  renderer, URL, имени файла или журнале;
- `node-keytar` как основной механизм (устарел); используется
  `safeStorage`.

### «Запомнить»

- По умолчанию выключено; после успешного открытия пользователь может
  включить сохранение ключа.
- В системное хранилище попадает 32-байтовый мастер-ключ, а не пароль.
- Зашифрованный `safeStorage` blob пишется в `userData` с правами `0600`;
  путь не является секретом.
- На Linux проверяется `safeStorage.getSelectedStorageBackend()`: если
  выбран `basic_text` или шифрование недоступно, «Запомнить» отключается и
  пароль запрашивается при каждом запуске.
- Electron выводит ключ из пароля и sidecar в main-процессе (`@noble/hashes`, Argon2id),
  поэтому в `safeStorage` попадает именно raw-ключ.
- Смена пароля из desktop-клиента обновляет `safeStorage`: main-процесс после
  успешной перешифровки выводит новый ключ из нового пароля и sidecar и
  перезаписывает blob. Если «Запомнить» не включено, старый blob удаляется.
- На Unix старый пароль при смене идёт в stdin, новый — в fd 3. На Windows
  дополнительный fd не гарантирован, поэтому новый пароль пишется во временный
  файл `0600` в пользовательском `%TEMP%` и удаляется сразу после завершения
  `asledgerctl`; в argv/env содержится только путь, не секрет.
- `asledgerctl passwd` сам `safeStorage` не обновляет: старый blob становится
  неверным, приложение удаляет его при ошибке открытия и просит новый пароль.
  При следующем успешном открытии с «Запомнить» blob перезаписывается
  атомарно.
- При выходе/остановке ключ удаляется из памяти best-effort; JS-строки и
  Go-срезы не гарантируют затирание, это остаточный риск.

### Fallback «KDF-результат в config.json»

В `v1.3.0` **не поддерживается**. Если системного хранилища нет, приложение
спрашивает пароль при каждом старте. Это осознанное решение: ключ в
`config.json` эквивалентен отсутствию шифрования для облачной папки.
Небезопасный режим можно добавить только отдельным решением с явным
предупреждением и не по умолчанию.

## 6. Жизненный цикл ключа

1. **Создание книги.** Пользователь задаёт пароль; генерируется соль;
   Argon2id выводит ключ; создаётся sidecar; SQLCipher создаёт книгу с raw
   key; выполняется миграция схемы; ключ остаётся только в памяти.
2. **Обычное открытие.** Пароль из источника → Argon2id → ключ → SQLCipher.
   Неверный ключ даёт `file is not a database`; исходный файл не изменяется.
3. **«Запомнить».** После успешного открытия ключ шифруется `safeStorage` и
   сохраняется; при следующем старте берётся оттуда.
4. **Смена пароля.** Старый ключ подтверждает доступ; генерируется новая
   соль; новый ключ; книга перешифровывается в новый файл; проверяется
   чтение; старый файл заменяется атомарно; sidecar обновляется. Desktop-
   клиент после этого обновляет keychain; `asledgerctl passwd` оставляет
   обновление `safeStorage` приложению. Перед операцией создаётся резервная
   копия.
5. **Остановка.** Ключ удаляется из памяти; SQLCipher закрывает WAL;
   `safeStorage`-blob остаётся только если включено «Запомнить».
6. **Удаление.** Пользователь удаляет книгу, sidecar, keychain-запись и
   резервные копии; приложение не хранит скрытую копию ключа.

## 7. Восстановление, смена и откат

- **Забыл пароль.** Восстановления by design нет. Если «Запомнить» включено и
  системное хранилище доступно, книгу можно открыть и задать новый пароль.
  Иначе нужна резервная копия и старый пароль/ключ; иначе данные теряются.
- **Смена пароля.** Только с подтверждением старого пароля/ключа. Перед
  операцией — резервная копия; после — проверка чтения и целостности; при
  ошибке старый файл остаётся нетронутым.
- **Откат на `v1.2.0`.** Старая версия не умеет SQLCipher. Для отката нужна
  незашифрованная копия, сделанная до миграции, либо экспорт данных. Plaintext
  копия не должна оставаться после успешной миграции; временная копия
  удаляется, но SSD может сохранить блоки — это остаточный риск.
- **Резервные копии.** `asledgerctl backup` и `VACUUM INTO` создают
  зашифрованную копию тем же ключом и копируют рядом sidecar `<db>.kdf.json`.
  `migrate-encrypt` и `passwd` дополнительно проверяют новую книгу открытием и
  `PRAGMA integrity_check`; для `backup` проверка ограничена успешным
  `VACUUM INTO`. Пароль/ключ рядом с копией не хранится. Старые
  незашифрованные копии пользователь удаляет сам; приложение предупреждает.
- **Миграция plaintext → SQLCipher.** `asledgerctl migrate-encrypt` открывает
  книгу только по явной команде, делает checkpoint и `integrity_check`,
  экспортирует данные в новый зашифрованный файл, проверяет его новым ключом и
  только затем заменяет книгу. Резервная копия создаётся сразу зашифрованной
  (новым ключом), поэтому plaintext-копия после успеха не остаётся. `-dry-run`
  проверяет книгу без изменений.
- **Смена пароля.** `asledgerctl passwd` подтверждает старый пароль/ключ,
  перешифровывает книгу в новый файл, проверяет целостность, сохраняет
  зашифрованную резервную копию старой книги и её sidecar, затем атомарно
  заменяет книгу и sidecar. При ошибке старый файл и старый sidecar остаются
  рабочими. В desktop-клиенте кнопка «Сменить пароль» останавливает сервер,
  запускает `asledgerctl passwd` со старым паролем в stdin и новым в fd 3
  (на Windows — через временный файл), обновляет `safeStorage` и перезапускает
  сервер с новым паролем.
- **WAL.** Перед копированием/миграцией выполняется checkpoint; `-wal` и
  `-shm` не копируются отдельно от согласованной книги.

## 8. Журналы, дампы и renderer

- В журнал пишутся факт открытия/закрытия, тип ошибки и время; пароль, ключ,
  DSN с ключом и производные значения не пишутся.
- Ошибка неверного пароля не должна содержать введённое значение или ключ.
- Electron renderer не получает сохранённый ключ и не имеет доступа к Node.js.
  Пароль вводится в отдельном доверенном окне; после передачи в main он
  очищается best-effort. Окно книги не имеет preload и не может вызвать
  desktop IPC.
- `crashReporter` не включается; для systemd задаётся `LimitCORE=0`.
- Сторонние библиотеки не должны логировать DSN/параметры подключения; DSN с
  ключом не передаётся в общие логгеры.

## 9. Сборка и CI

Spike #148 подтвердил:

- Linux amd64: зашифрованная книга, WAL, `VACUUM INTO`, миграция
  `sqlcipher_export`, неверный ключ, `modernc.org/sqlite` не читает файл;
- Linux arm64 и Windows amd64: кросс-сборка с cgo;
- GoReleaser-cross 2.18.3 (Go 1.26.10) собрал три цели примерно за 53 с;
- статическая линковка: `ldd` не показывает динамических зависимостей;
- Windows-бинарник зависит только от `KERNEL32.dll` и `msvcrt.dll`;
- размер прототипа с двумя драйверами — 8–9 МиБ; после удаления
  `modernc.org/sqlite` ожидается меньше.

Требования к релизной сборке:

```text
CGO_ENABLED=1
tags: netgo osusergo sqlite_omit_load_extension
ldflags: -s -w -linkmode external -extldflags "-static"
CC:
  linux/amd64   gcc
  linux/arm64   aarch64-linux-gnu-gcc
  windows/amd64 x86_64-w64-mingw32-gcc
```

GoReleaser запускается в `goreleaser/goreleaser-cross`; версию/дайджест образа
нужно закрепить, а не использовать `latest`. Сборочный образ должен содержать
`gcc`, `aarch64-linux-gnu-gcc`, `libc6-dev-arm64-cross` и
`x86_64-w64-mingw32-gcc`. Время CI увеличивается на компиляцию SQLCipher;
ориентир spike — около минуты на три цели.

Влияние на репозиторий:

- `make check`/`make build` на Linux требуют gcc и `CGO_ENABLED=1`;
- Windows CI ставит MinGW через MSYS2 и добавляет `mingw64/bin` в `PATH`;
  иначе unit-тесты `store` на Windows не соберутся;
- `desktop/scripts/build-backend.mjs` собирает cgo с `CC` для
  linux/arm64 и windows/amd64 и статической линковкой; CI ставит
  `gcc-aarch64-linux-gnu` и MSYS2;
- GoReleaser запускается в `ghcr.io/goreleaser/goreleaser-cross:v1.26.10`;
  версия закреплена, при обновлении Go её нужно поднять вместе с `go.mod`;
- macOS в релизную матрицу `v1.3.0` не входит;
- при провале сборки любой целевой платформы релиз блокируется. Fallback на
  `modernc.org/sqlite`/plaintext в релизе запрещён.

## 10. Проверки spike #148

Прототип находится вне репозитория и не является кодом `v1.3.0`. Основные
результаты:

- `PRAGMA cipher_version` → `4.4.2 community`;
- заголовок файла не `SQLite format 3`, маркер `секретный счёт` в книге и
  WAL не найден;
- неверный ключ → `file is not a database`;
- `modernc.org/sqlite` → `file is not a database (26)`;
- `VACUUM INTO` создаёт зашифрованную копию, которая читается ключом;
- `sqlcipher_export` переносит plaintext-книгу в SQLCipher;
- WAL включается, `PRAGMA integrity_check` → `ok`;
- 5000 вставок после открытия: SQLCipher ~4 мс, `modernc` ~4–5 мс;
- открытие существующей книги с паролем SQLCipher ~257–261 мс (KDF), с raw
  key — 0 мс.

### Проверки S24 (#160)

На Linux amd64 (Go 1.27.1, gcc 16.2.1) проверено:

- `PRAGMA cipher_version` → `4.19.0 community`,
  `select sqlite_version()` → `3.53.4`;
- книга, созданная драйвером 4.4.2, открывается, `PRAGMA integrity_check` →
  `ok`, миграции и `sqlcipher_export` проходят;
- книга, созданная драйвером 4.19.0, открывается драйвером 4.4.2 с тем же
  raw-key и `cipher_page_size=4096`;
- параметры книги сохраняются: `cipher_page_size=4096`,
  `kdf_iter=256000`, `HMAC_SHA512`, `PBKDF2_HMAC_SHA512`;
- кросс-сборка Linux amd64/arm64 и Windows amd64 в
  `goreleaser-cross:v1.26.10` проходит; Linux-бинарники статические,
  Windows зависит от `ADVAPI32.dll`, `KERNEL32.dll`, `msvcrt.dll`;
- `libcrypto`/OpenSSL в линковке нет — используется вендорный libtomcrypt.

Регрессия закреплена тестом `TestOpenBookFromSQLCipher442` и фикстурой
`pkg/core/store/testdata/sqlcipher-4.4.2.db`.
