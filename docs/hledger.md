# Импорт и выгрузка hledger

asledger переносит историю в plaintext-формате
[hledger](https://hledger.org/) — это формат для миграции с другого
инструмента и выгрузки книги во внешние программы. Пакет `pkg/core/hledger`
содержит парсер (`parse.go`), писатель (`write.go`), импортёр (`import.go`) и
выгрузку (`export.go`).

## Разбор книги

Парсер читает подмножество формата, достаточное для реальных книг:

- проводки: строка с датой и описанием, ниже — строки счетов с суммами;
- директивы `account` (в т.ч. с комментарием-типом), `include` отклоняется;
- комментарии `;` и блочные `comment … end comment` пропускаются;
- `P`, `D`, `Y` и прочие директивы игнорируются без ошибки.

Ошибка одной проводки не прерывает разбор: остальные читаются, а проблемные
попадают в отчёт (`Book.Errors`) и в `Book.Dropped` — число блоков, не ставших
проводками.

### Суммы

Разделители разрядов — пробел, `U+00A0` и `U+202F`; десятичный разделитель —
точка или запятая:

- `1 234,56`, `1 234.56`, `1,234.56` → 1234,56;
- если есть и точка, и запятая, разряды отделяет **левый** знак;
- одиночный знак без пробелов считается десятичным: `1,234` → ошибка точности,
  а не 1234 (защита от случайного ×1000).

Обозначение рубля (`₽`, `р.`) можно указывать, оно отбрасывается.

### Строки проводки

- Официальный разделитель счёта и суммы — два и более пробелов или табуляция.
  Всё после разделителя обязано быть суммой, иначе это ошибка разбора.
- Один пробел допускается только для недвусмысленной суммы (со знаком,
  разделителем или обозначением рубля).
- Пропущенную сумму одной строки парсер восстанавливает как остаток проводки.
- Виртуальные проводки `(…)` и `[…]`, а также `include` отклоняются.

### Типы счетов

Тип счёта восстанавливается по порядку:

1. из действующего плана счетов asledger (весь счёт и его поддерево);
2. из комментария директивы `account … ; тип: расход` (точный round-trip типов);
3. по имени корневого счёта: `актив(ы)/имущество/assets`, `пассив(ы)/обязательства/долг(и)/liabilities`,
   `капитал/equity/capital`, `доход(ы)/income`, `расход(ы)/expenses`.

Если корень неизвестен, импорт сообщает проблему с подсказкой — добавьте
директиву `account … ; тип: …`.

## Режимы импорта

| Режим | Поведение |
| --- | --- |
| «гибкий» (по умолчанию) | дополняет план счетов недостающими счетами, проблемные проводки пропускает с причиной |
| «строгий» | при первой же проблеме (в т.ч. неизвестном счёте) книга не меняется, счета не создаются |

Строгий режим удобен для проверки выгрузки: отчёт перечисляет всё, что мешает
переносу. Гибкий не требует готового плана счетов.

## Стороны и тип операции

Знак суммы задаёт сторону строки: плюс — дебет, минус — кредит; суммы всегда
положительны. Строки одного счёта и одной стороны складываются (в книге
asledger на пару «счёт + сторона» приходится одна строка), нулевые строки
отбрасываются. Если после объединения осталось меньше двух строк, проводка
пропускается.

Сторону по-прежнему назначает исходная книга, а тип операции (`op_type`)
выводится эвристикой по типам счетов:

| Признак | Тип операции |
| --- | --- |
| расход на дебете | трата |
| доход на кредите | доход |
| только активы | перевод |
| пассив на кредите | выдача займа |
| пассив на дебете | погашение долга |
| только капитал | начальные остатки |
| иначе | корректировка |

## Идемпотентность

Проводка получает `source = hledger` и `source_hash` —
SHA-256 от источника, каноничного текста проводки и номера повторения. uuid
выводится из того же хеша. Повторный импорт того же файла не создаёт новых
проводок: они попадают в `duplicates` отчёта. Частичный уникальный индекс
`(source, source_hash)` (миграция `0003`) защищает и на уровне БД.

Две одинаковые проводки в одной книге остаются двумя: номер повторения входит
в хеш.

## Запись

Импорт идёт в две фазы:

1. недостающие счета создаются идемпотентно (`store.EnsureAccounts`);
2. каждая проводка проходит `engine.ValidateImported`, затем все принятые
   проводки записываются одним коммитом в одной транзакции (`store.ApplyCommit`).

Ошибка создания счетов не оставляет частичного состояния: отчёт помечается
`rejected`, книга не меняется.

`ValidateImported` проверяет суммы, стороны, существование/листовость/архивность
счетов, баланс ΣDEBIT = ΣCREDIT и верхнюю границу даты, но не применяет матрицу
операций и нижнюю границу «дата не раньше создания счёта» — импортируется
историческая книга.

## Выгрузка

`hledger.Export` пишет план счетов директивами `account` (с комментарием-типом и
`min_balance`) и проводки. Флаг `IncludeArchived` включает архивные счета.
Круговая проверка «выгрузка → импорт» даёт ту же книгу
(`TestASL_8_ExportImportRoundTrip`).

Кроме hledger есть CSV (`pkg/core/export`: журнал, остатки, обороты) и
полноценный JSON-снапшот (`sync.Snapshot`) — полная резервная копия книги.

Plaintext-формат не переносит всё состояние: `min_balance` и признак архива
восстанавливаются из директив `account`, а пользователи, устройства, токены и
настройки переносит только JSON-снапшот.

## Применение

- REST API: `POST /api/v1/import` (`format=hledger`), `GET /api/v1/export`
  (`format=hledger|csv|json`) — см. [api.md](api.md).
- Web: страница «Данные» (`GET /data`) — см. [web.md](web.md).
- CLI: `asledgerctl import hledger <файл>`, `asledgerctl export hledger|csv|json`.
