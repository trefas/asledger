# Списки покупок

Документ описывает эпик «Списки покупок» (#165): модель данных, пользовательский
сценарий, REST API, web-интерфейс и инварианты проведения.

## Зачем это нужно

Список покупок отделяет планирование от учёта. Пользователь заранее собирает
товары, распределяет их по статьям расходов и ответственным, а в магазине
фиксирует фактическую цену или отметку «в корзине». В книгу попадают только
реально купленные позиции; остальные остаются в списке для следующего похода.

Эпик закрывает четыре пользовательские истории:

- **US-1** — создание и настройка списка до магазина;
- **US-2** — фиксация цен, отметка «в корзине» и расхождений с ценником;
- **US-3** — оформление подтверждённых позиций в проводки;
- **US-4** — повторное использование списков через шаблоны.

## Модель данных

Все суммы хранятся целыми копейками, время — unix-секундами. Списки живут в той
же зашифрованной книге SQLCipher, что и проводки.

### `shopping_lists`

| Поле | Назначение |
| --- | --- |
| `id`, `uuid` | идентификаторы списка |
| `name` | название |
| `planned_date` | дата похода, `0` — не задана |
| `status` | `draft`, `active`, `shopping`, `completed`, `archived` |
| `owner_id` | владелец списка |
| `created_at`, `updated_at`, `archived_at` | время создания, изменения и архивации |

### `shopping_items`

| Поле | Назначение |
| --- | --- |
| `id`, `uuid`, `list_id` | идентификаторы и принадлежность списку |
| `name` | наименование товара |
| `account_id` | статья расходов (листовой счёт типа «расход»), может быть пустой в черновике |
| `assignee_id` | ответственный |
| `priority` | `low`, `normal`, `high` |
| `planned_price_kop` | ориентировочная цена |
| `actual_price_kop` | фактическая цена в магазине |
| `in_cart` | товар в корзине, цена может быть неизвестна |
| `price_mismatch` | зафиксировано расхождение с ценником |
| `comment` | комментарий |
| `status` | `planned`, `confirmed`, `purchased`, `skipped` |
| `position` | порядок в списке |
| `version` | версия для оптимистичной блокировки |

Позиция считается **подтверждённой**, если `actual_price_kop > 0` или
`in_cart = 1`. Только подтверждённые позиции попадают в итог и в проводку.

### Шаблоны

`shopping_list_templates` и `shopping_template_items` хранят только базовые
поля: наименование, статью расходов и приоритет. Цены, ответственные и статусы
в шаблон не копируются, поэтому из одного шаблона получаются независимые
списки.

## Пользовательский сценарий

1. **Список.** На странице «Покупки» создайте список: название, дата, владелец.
   Добавьте товары, статьи расходов, ответственных и приоритеты.
2. **Магазин.** Откройте режим магазина на телефоне. Для каждой позиции
   введите фактическую цену или отметьте «в корзине». При расхождении с
   ценником поставьте флаг и комментарий. Итог считается только по
   подтверждённым позициям.
3. **Оформление.** На экране «Оформить покупку» проверьте статьи и суммы,
   выберите один или несколько счетов оплаты. Предпросмотр показывает строки
   будущей проводки и итоги дебета и кредита, но книгу не меняет.
4. **Проведение.** Кнопка «Провести покупку» записывает проводку, переводит
   позиции в `purchased` и добавляет записи аудита одной транзакцией БД.
   Неподтверждённые позиции остаются в списке.
5. **Повторное использование.** Сохраните список как шаблон и создавайте по
   нему новые списки в один клик.

### Статусы

- `draft` — черновик;
- `active` — список в работе;
- `shopping` — пользователь в магазине;
- `completed` — все позиции куплены или пропущены;
- `archived` — список в архиве, изменения запрещены.

Позиция: `planned` → `confirmed` (цена или «в корзине») → `purchased` после
проведения. `skipped` означает, что товар не куплен и не мешает завершить
список.

## Инварианты проведения

- В проводку попадают только подтверждённые позиции выбранного списка.
- Одна транзакция БД: проводка + статусы `purchased` + аудит. Ошибка любой
  позиции откатывает всё.
- Идемпотентность по `uuid` проводки (в web-форме — скрытое `request_id`):
  повтор не создаёт дубль и возвращает уже записанную проводку.
- ΣDEBIT = ΣCREDIT; строки проверяются движком по матрице ASL-2.2.
- Несколько товаров с общей статьёй расходов дают одну строку проводки с
  суммарной суммой: таблица `transaction_lines` хранит не больше одной строки
  на счёт и сторону.
- После покупки последней позиции список переходит в `completed`.
- Купленную позицию нельзя удалить; архивный список нельзя менять.

## REST API

Полное описание — в [api.md](api.md). Кратко:

| Метод | Назначение |
| --- | --- |
| `GET/POST /api/v1/shopping-lists` | список списков и создание |
| `GET/PATCH/DELETE /api/v1/shopping-lists/{id}` | чтение, изменение, архивация |
| `POST /api/v1/shopping-lists/{id}/items` | добавить позицию |
| `PATCH/DELETE /api/v1/shopping-items/{id}` | изменить или удалить позицию |
| `GET/POST /api/v1/shopping-list-templates` | шаблоны и создание |
| `GET/PATCH/DELETE /api/v1/shopping-list-templates/{id}` | чтение, изменение, удаление |

Обновление позиции требует `version`; при устаревшей версии возвращается `409`
`ERR_SHOPPING_VERSION_CONFLICT`.

`POST /api/v1/shopping-lists` принимает `template_id`: базовые позиции
копируются из шаблона, пустое название заменяется названием шаблона.

## Web-интерфейс

Полное описание — в [web.md](web.md). Основные адреса:

- `/shopping-lists` — списки, создание, создание из шаблона;
- `/shopping-lists/{id}` — позиции, сохранение как шаблон, архивация;
- `/shopping-lists/{id}/shop` — режим магазина;
- `/shopping-lists/{id}/checkout` — оформление и предпросмотр;
- `/shopping-templates` — шаблоны и их правка.

Web-интерфейс адаптирован под телефон: крупные поля и кнопки, итог закреплён
сверху в режиме магазина. Android-клиент не меняется: мобильный сценарий идёт
через web-UI в локальной сети.

## Синхронизация

`GET /api/v1/sync/snapshot` и `GET /api/v1/sync/pull` дополнительно отдают
массивы `shopping_lists`, `shopping_items` и `shopping_list_templates`.
`format_version` остаётся `1`: старый Android-клиент игнорирует неизвестные
поля и продолжает работать.

## Аудит и отчёты

Создание, изменение и удаление списков, позиций и шаблонов пишется в журнал
изменений (`changelog`). Проведённая покупка — обычная проводка: она видна в
журнале, остатках, оборотах и отчёте расходов.
